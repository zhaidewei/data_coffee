# 100 用户、20 人并发的修复设计

读者：实现与评审此轮修复的开发者。目标是在现有 Workers + D1 架构上减少真实操作冲突和首页读取成本，并保持通知可靠性。

## 1. 报名并发
首次报名允许在其他用户报名导致版本变更后，重新校验最新状态并有限重试。使用数据库 CAS 和原有幂等键，保证不超额、不重复记账、不重复生成通知。仅对首次 join 放宽全局版本要求，audit 须证明中间所有版本都是其他人的 join；涉及本人既有状态、时段变更和管理决策时保留冲突保护，不允许旧请求覆盖新的本人意图。关键管理操作仍要求精确版本。

验收：20 人携同一初始版本报名同一活动，全部得到合法结果；3 个席位产生 3 人报名和 17 人候补。覆盖重复请求、截止、取消、同用户冲突和严格管理版本。

## 2. 首页分页
服务端默认每页 12 场，上限 20 场，稳定排序；筛选在分页之前执行，城市和主题统计覆盖匹配全集。前端切换筛选回到第一页，保留日期、城市、主题和地图语义。列表批量取活动文档，避免对每条未到期活动再查询一次。到期活动保留规则推进，不展示过期决策。CLI 遵循返回的分页信息，避免静默截断。

验收：超过一页时可翻页，边界稳定，筛选可找到后续页活动，私人草稿不泄漏，未到期页查询次数不随卡片数量线性增加。

## 3. 通知减量
保留登录优先预算、持久 outbox、租约、失败重试和供应商幂等机制。第一轮仅合并同一收件人尚未发送的“有新的待处理申请”通知，正文保留每项变更及活动链接；不延迟或吞掉候补确认等有期限的必要消息。重试使用稳定发送内容与标识，避免一次发送成功但确认失败后重复发信。每日额度不自动扩大，不新增外部服务。

验收：合并内容完整；并发 drain 不重复领取；失败后可恢复；登录保留额度继续有效。若现有结构不能安全聚合，先实现可证实安全的减量并记录剩余限制。

## 交付边界
三块分别实现和测试，再统一类型检查、单元测试与浏览器验证。当前「测试阶段」标识保留。本轮不 commit、不部署、不向真实用户发送测试邮件。

## 实现取舍与容量边界

- 报名最多 10 次 CAS，指数随机退避；普通首次报名路径最多约 40 条 SQL，到期结算、通知和 HTTP 身份/投影查询另计。保护优先，重试耗尽仍明确返回冲突。
- 列表当前批量扫描可见活动文档后筛选分页，返回每页 12 场；此轮消除未到期活动的 N+1 查询，但数据库读取量仍随活动总量增长。大量活动同时到期时仍需逐项推进，这是后续独立的调度预算工作。
- 本地并发结果用于验证一致性，不能替代线上网络时延和云端限额测试。邮件额度不因本轮修复增加。

## 验收结果（2026-09-08）

- 16 个测试文件、226 项测试全部通过。新增测试包含真实 HTTP 登录会话携同版本的 20 人并发报名、独立 D1 binding 竞争、相同幂等键重放、同用户旧意图、AI 提案严格版本和提交前竞争。
- 隔离 D1 场景：100 个测试用户中 20 人同时首次报名，得到 3 人报名、17 人候补，20 条报名审计，无重复报名。
- 浏览器 mock 25 场：三页完整显示，筛选回第一页，旧异步响应不能覆盖最新筛选，测试阶段标识可见，无页面脚本错误。真实本地 API 返回分页响应。
- 通知独立评审发现的吞吐及优先级问题已修复：候补/期限/补齐最高优先，普通其次，申请汇总最低。普通独立邮件成功路径 7 条 SQL，每批预算 40 条下可发送 5 封（含清理 39 条）；失败恢复额外预留。此预算只覆盖 drainMail，未覆盖前面的 tick，不能据此承诺整个 cron 永远符合平台限额。
- AI 精确版本授权的既有测试发现回归，现通过显式 strictVersion 在每轮 CAS 内检查，独立复审通过。
- `0006_mail_digest.sql` 已应用本地。未来发布需先迁移远端；已有 mail_dispatch 但缺少原始 payload 的未决发送会进入人工核对，避免无法证明原发送内容时再次发送。
- 未提交、未部署、未发送真实邮件。大量同时到期的调度预算、独立通知积压和实际云端容量仍是后续验收项。
