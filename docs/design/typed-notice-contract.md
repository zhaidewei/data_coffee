# 通知语义契约

读者：维护领域事件、通知发送器与数据库迁移的开发者。关注点是修改展示文案时不改变投递行为，以及旧队列在升级后如何继续处理。

`Notice` 必须带 `kind`、`priority`、`deliverBefore`。领域产生点通过 `worker/notices.ts` 生成语义；`store` 将字段原值写入 outbox 的 `kind`、`priority`、`deliver_before`。`subject` 和正文只负责展示，发送器不解析中文文案。

优先级数值越小越先处理：0 为候补和补齐期限消息，1 为常规通知，2 为申请提醒。相同优先级先处理有期限的通知，再按期限、产生时间和 id 稳定排序。`deliverBefore` 是业务给出的期望投递时限；本轮不引入超期丢弃或补偿策略，过期积压仍可观察且继续遵循原重试规则。

只有 `application_submitted`、优先级 2、无期限的未发送提醒可建立新聚合。成员保留各自完整正文及链接；已经冻结的请求跨重试保持不变。新的通知类型默认应独立发送，加入聚合白名单需要显式修改中央策略并测试。

迁移 `0008_outbox_notice_kind.sql` 只追加字段和索引。旧记录统一使用 `legacy_unknown`、优先级 0、未知期限，不根据标题反推类型，也不建立新聚合。已经持久化的旧分组继续使用成员关系和原冻结请求完成恢复。已发送记录的正文、状态、成员关系和请求内容保持原值。

部署前必须先应用迁移再切换发送器和通知写入代码。当前分支允许暂缺并行变更的 0007，合并时按主分支迁移顺序重新验证。本次不修改 cron、每日邮件额度、Activity 版本或前端。
